# Задания на моделирование — отдельно от 50 SQL-задач

**М1 (10 минут).** По исходному описанию нарисуй концептуальную ER/UML-модель: пользователь, роли заказчика и фрилансера, проект, заявка, отзыв. Укажи атрибуты и кратности. Сначала сделай свою версию, затем сравни с `schema.svg` / `schema.mmd`.

**М2 (15 минут).** Напиши свой DDL в `my_schema.sql`. Проверь первичные/внешние ключи, денежные типы, обязательность полей, положительные суммы, диапазон рейтинга, уникальность заявки человека на проект и единственность принятой заявки. Эталон в `../sql/schema.sql`. Эти два задания проверяются по чек-листу вручную: эквивалентных моделей несколько.

## Принятые решения

- `users` содержит общие атрибуты. `customers` и `freelancers` — роли с PK, одновременно являющимся FK на пользователя. Допускается совмещение ролей; пользователь может еще не получить ни одной роли.
- Заказчик → проект: 1 к 0..N. Каждый проект имеет ровно одного заказчика.
- Фрилансер → заявка: 1 к 0..N. Проект → заявка: 1 к 0..N. Связь фрилансер–проект M:N раскрыта через заявку.
- Одна заявка человека на проект: `UNIQUE(project_id, freelancer_id)`.
- Максимум одна принятая заявка на проект: частичный UNIQUE INDEX, не обычный `UNIQUE(project_id,status)` — последний ошибочно запретил бы несколько отклоненных заявок.
- `completed_at` добавлен явно: без даты завершения невозможно корректно решить отчет за прошлый месяц. `created_at` нужен для хронологии.
- Один отзыв на проект. Автор однозначно определяется заказчиком проекта, получатель — принятой заявкой. Не храним дублирующие ID автора/исполнителя. Отзыв возможен только после завершения.
- Денежные значения — `numeric`, не `float`. Даты событий — `timestamp` (для тренировки в одной зоне Europe/Moscow), обещанный день завершения — `date`.
- При принятии/отклонении фиксируются разные поля времени. CHECK связывает статус с заполненностью этих полей.

## Что не выражается простым CHECK

Связь статуса проекта с наличием принятой заявки; запрет отзывов до завершения; автоматическое отклонение конкурентов. Межтабличные проверки и действия вынесены в `../sql/workflow.sql`: отложенные constraint triggers и транзакционные функции `choose_bid` / `complete_project`. Это дополнительный материал, не обязательный объем ответа CREATE TABLE на контрольной.

Функции выбора и завершения используются администратором в одной транзакции; учебная роль доступна только для чтения. `choose_bid` блокирует строку проекта, выбирает одну заявку и отклоняет остальные. Если требуется проверить итог сразу внутри транзакции, используй `SET CONSTRAINTS ALL IMMEDIATE` после завершения всех изменений.

## Чек-лист самопроверки

- [ ] У каждого отношения есть PK, все ссылки оформлены FK.
- [ ] Имя не используется как PK: имена могут совпадать.
- [ ] Бюджет, ставка и цена заявки положительные и точные.
- [ ] Повторная заявка человека на тот же проект запрещена.
- [ ] Несколько отклоненных заявок допустимы, две принятые — нет.
- [ ] Дата завершения проекта существует и согласована со статусом.
- [ ] Рейтинг ограничен 1..5, не допускает NULL.
- [ ] Кратности на диаграмме совпадают с DDL.
- [ ] Объяснено, что реализуется CHECK/UNIQUE, а что функциями/триггерами.
